# Runtimes

Each folder implements the autoresearch harness for one runtime. Pick the most specific folder that fits the target repo, copy it into the repo (for example to `perf/`), and adapt the documented extension points.

| Folder | Use for | Pairing |
|---|---|---|
| `node-ts/` | JavaScript and TypeScript libraries on Node.js | In-process: both revisions loaded as separate module instances, both load orders |

There is one folder, because there has been one ecosystem. For anything else, write a folder against the contract below and keep it: a harness that has run a campaign is worth shipping, one that has not is a guess with a table of contents.

## Contract for a runtime folder

A runtime folder must provide these capabilities. The method in `SKILL.md` depends on each of them.

1. **A/B timing of two revisions.** Takes two git revisions, the second one defaulting to the working tree. Materialises each committed revision with `git archive` into its own directory (one per side, so a revision compared with itself gives two real copies). Times the same deterministic cases on both sides in alternation, swapping the order on every iteration. Discards warm-up iterations. Reports per case the absolute times (per-side minima), the delta as the **median of the per-iteration ratios**, and the dispersion of those ratios; then two summaries, time-weighted and equally weighted. Where the runtime allows two copies in one process, it measures in-process and cancels load-order bias by running both orders.
2. **A case filter** (`--only`), honoured by every script. A run limited to the case a change targets is what makes a per-case decision possible on a machine whose full-suite bands are too wide, and it must be one filter in one place, or each campaign reimplements it in its own cases file.
3. **A machine verdict after the run**, not only before it: a short probe once the timing has finished, printed with the results. A run is only data if the machine was quiet for all of it, which nothing can know in advance.
4. **Characterisation guard.** Runs the cases' behaviour samples against a revision (default: the working tree), hashes them, and compares with recorded expectations. Any difference exits non-zero. `--update` samples **twice** and refuses to record a key that moved, so a case that samples randomness or mutates its own input cannot be written into the expectations. Once the file exists, `--update` may only add keys: an existing key whose hash changed is a failure, which is how "never update the guard to make a change pass" stops depending on memory. Recording against a named revision is what a case added mid-campaign needs.
5. **Profiler helper.** Profiles the cases against the working tree and prints self and total time per function, without frames from dependencies or the runtime's loader, plus an aggregation by path prefix that answers how much of the profile is the instrument rather than the library.
6. **Example cases.** One case definition, with seeded data, feeds both the A/B harness and the guard. Async bodies are supported, and the example says why a fixed batch per call is mandatory for them.
7. **A machine-readiness probe.** Times one pure CPU loop repeatedly and reports how far the median sits above the minimum, so a campaign does not calibrate against someone else's build.
8. **Standalone timing, one revision per process**, in two forms: one case against one revision, to confirm a per-case delta the paired harness reports on untouched code; and whole processes alternating A, B, A, B, which produces the number a PR is allowed to print. The second form prints each revision's spread across processes, because a case whose same-revision spread covers the effect cannot be measured this way at all, and it defaults to enough pairs and iterations to be a claim rather than a hint.
9. **A scaling scan**: each input shape at n and at a multiple of n, so superlinear paths show up. A suite built on realistic sizes cannot see them, and they are often the largest wins available. Two families of shape: growing the input, and growing the number of operations against one long-lived object.
10. **A differential check**: both revisions over generated and hand-picked inputs, compared on everything observable, for changes whose risky inputs the suite does not cover. Inputs that are not strings (objects, proxies, two values derived from one source) need named scenarios, because that is where a change that stops copying something is caught.
11. **A case-size report** before calibration, and **drift warnings** during a run. The first names bodies outside the usable range while the fixtures are still cheap to change. The second names a case that ran slower at the end of a run than at the start, which is the only way the harness can see a case that accumulates state (the minimum hides it and the paired ratio cancels it), and one that ran faster, which is a case that had not reached optimised code when timing began. Both fire only on **agreement between every side and every load order**: one of those values on its own reached 113% on a case that accumulates nothing, so a warning built on the worst of them fires on a third of a real suite and is then ignored.
12. **Build support**, when the shipped artifact is generated: the harness builds each materialised revision itself and never falls back to artifacts on disk.
13. **Optional: other metrics.** For example retained memory per instance, when maintainers value it.
14. **A README** with setup, commands, extension points and runtime-specific traps.

## Notes for new runtimes

- **In-process pairing is possible** when the runtime can load the same code twice under separate identities: JavaScript module instances (by file path), JVM class loaders, .NET AssemblyLoadContext. It is not practical for Python (module names are global per interpreter, native extensions cannot load twice) or for compiled languages.
- **Out-of-process pairing** covers everything else, and keeps every rule of the method except the load orders. Unpack each revision into its own directory, build it once per directory, then run the two benchmark commands alternately (A,B on even iterations, B,A on odd ones) so both sides of an iteration share the machine state. Keep the estimator: median of the per-iteration ratios for the delta, per-side minima for the absolute numbers, the two markers, both summaries. Expect a worse noise floor than in-process pairing and calibrate accordingly.
- **Language-native benchmark frameworks** (Rust criterion, Go `testing.B`, JMH, pytest-benchmark) are good case runners. Wrap them so each run prints one line per case with a duration, and parse that. Their own "compare with saved baseline" features compare two standalone runs, which is not paired, so do not use them for the decision. For Go, `benchstat` over interleaved runs is an acceptable alternative.
- **Per-case lifecycle and the guard** are not optional in a new runtime: without `setup`/`teardown` the inputs of every case stay alive on both sides, and without a guard the campaign has no evidence that anything it kept is behaviour-preserving.
- **Case lifecycle.** Cases need optional `setup`/`teardown` so large inputs exist only while their case runs; every harness script has to call them. Inputs of all cases alive at once exist twice, once per revision, and make every collection slower on both sides.
- **A self-test pays for itself here.** Tree construction is the part that fails silently: a tree that shares code with the working tree produces plausible numbers, and an over-eager resolution check blocks every run. A synthetic repo with one workspace package, one dependent and one shared package catches both in seconds (`node-ts/selftest.mts`).
- **Scratch directories** belong where the ecosystem's tooling already ignores them (for Node, inside `node_modules`). A git-level ignore hides them from git only, not from formatters, linters or type checkers.
- **Async workloads** are not optional in a runtime with a promise-based API. Await the body inside the timed region, require a fixed batch per call so the scheduling overhead is a constant that pairing cancels, and say that the returned promise must cover all of the work: a body that starts something and resolves before it finishes measures the scheduling and looks very fast.
- **Resolution leaks** are the main correctness risk of any harness: the materialised tree may still import code from the working tree (workspace packages resolved by name, installed editable packages, shared build caches). Always run the canary test from `SKILL.md` step 3 on a new setup.
